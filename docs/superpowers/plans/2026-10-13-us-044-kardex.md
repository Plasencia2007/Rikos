# Plan de Implementación: US-044 — Consultar el Kardex con origen rastreable

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implementar la consulta del Kardex de inventario por local con trazabilidad completa de orígenes, diferencias de stock, control de visibilidad de costos (RN-012), filtros dinámicos y navegación integrada desde Existencias.

**Architecture:** Monolito modular Spring Boot (`servicio-operacion`) con repositorio JPA y especificación dinámica `Specification<MovimientoInventario>` para filtrado multicriterio y paginación en base de datos. Control de acceso con Spring Security evaluando `PERM_inventario.ver` y filtrando costos con `PERM_inventario.ver_costos`. Frontend React/Vite (`rikos-web`) con pantalla ADM-17 detallada y enlaces cruzados desde ADM-16.

**Tech Stack:** Java 21, Spring Boot 3.3, Spring Data JPA / Hibernate, Spring Security (JWT), PostgreSQL 16, TypeScript, React 18, Tailwind CSS / Vanilla CSS, Lucide Icons, Playwright.

**Spec:** `docs/producto/flujos/08-ep08-inventario-produccion-compras.md` (§ US-044, RN-002, RN-012, RN-057).

## Global Constraints
- `movimiento_inventario` es un libro inmutable append-only; las consultas son de solo lectura y nunca alteran registros existentes.
- Cada movimiento debe asociarse a un origen obligatorio entre: `compra`, `produccion`, `venta`, `ajuste`, `transferencia`, `conteo`, `consumo_interno`, `anulacion_post_comanda` (RN-057).
- Cantidades y existencias se expresan con precisión decimal `NUMERIC(14,6)` en unidad base del producto.
- Los montos y costos se gestionan en céntimos de sol (`BIGINT`) o `BigDecimal` y se ocultan estrictamente si el usuario carece de `PERM_inventario.ver_costos` (RN-012).
- Orden cronológico configurable, por defecto `ocurrido_en DESC` para auditoría ágil.
- Paginación del lado del servidor para soportar grandes volúmenes de transacciones.

## Review Focus
1. Filtrado dinámico combinado: cuando se envían múltiples filtros simultáneos (localId + productoId + origen + rango de fechas), la consulta SQL debe combinar condiciones con `AND` respetando índices.
2. Ocultamiento de costos: usuarios con `inventario.ver` pero sin `inventario.ver_costos` deben recibir `costoUnitario = null` y `costoTotal = null` sin errores ni excepciones.
3. Rango de fechas con zona horaria: el filtro `desde` y `hasta` debe cubrir todo el rango del día local (`00:00:00` a `23:59:59.999999`) al recibir fechas tipo `YYYY-MM-DD`.
4. Visualización de signos y stocks: un movimiento de entrada debe mostrar `+cantidad` y `stockAnterior + cantidad = stockNuevo`; una salida debe mostrar `-cantidad` y `stockAnterior - cantidad = stockNuevo`.
5. Preselección desde Existencias: al ingresar a `/admin/inventario/kardex?productoId=XYZ`, el filtro de producto debe inicializarse automáticamente con dicho ID.
